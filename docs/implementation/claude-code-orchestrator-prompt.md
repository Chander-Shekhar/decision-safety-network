You are the execution orchestrator for the Decision Safety Network AI Builder Cup Core MVP. Work from the repository root. The founder has approved the locked Core MVP PRD, accepted Google Cloud/TypeScript architecture, detailed implementation plan, and UI wireframes. Your job is to manage the entire **subagent-driven implementation → independent review → correction → re-review → local integration → verification** loop. The founder retains product and external-action authority; Codex will conduct a later holistic review. Do not turn this into a new brainstorming or planning exercise, and do not personally implement every work package in one long context.

1. Read `CLAUDE.md` and `AGENTS.md` in full, then `README.md` and `project/WORKFLOW.md`. Read the locked `Decision_Safety_Network_PRD_Draft.md` Part I, the accepted record in `project/decisions/`, `docs/superpowers/specs/2026-09-30-core-mvp-technical-architecture-design.md`, `docs/superpowers/plans/2026-10-02-core-mvp-implementation-plan.md`, `docs/design/wireframes/README.md`, and `docs/submission-requirements.md`. 2. Inspect `git status`, branches/worktrees, recent commits, and the canonical `project/tasks/` directories. Do not assume a task is absent, done, or safe to overwrite from this prompt or prior chat. Preserve any user or other-agent edits. If the plan or wireframes are missing from your checkout, stop and report the exact Git state; do not silently recreate them. Do not automatically pull, reset, force-push, or discard work.
3. Confirm the approved plan's task-to-wireframe map resolves, the PRD is unchanged, and the Git identity is personal/no-reply—not a workplace address. ## Run the canonical task loop

Use the approved plan's Tasks 1–13 (DSN-003 through DSN-015), dependencies, owned paths, acceptance checks, and exact verification commands. Create or reconcile bounded DSN records in `project/tasks/` from `project/tasks/TEMPLATE.md`; do not create a second task board, status document, memory file, or competing checklist. Local task records remain canonical unless the one-time GitHub migration condition in `project/WORKFLOW.md` is actually met for **all** agents. Your own GitHub login alone does not prove that condition.

For each ready work package:

1. As the serialized integrator, claim it on shared local `main` exactly as `project/WORKFLOW.md` requires, with one owner, branch/worktree, dependencies, and exact owned paths. Create its isolated task worktree only from that committed claim. Enforce the plan's dependency order; parallelize only non-overlapping ready work. Shared contracts, root configuration, lockfile, and integration files are serialized. Never let two writers edit an overlapping path.
2. Dispatch a **fresh implementation subagent** with a narrow brief: objective; specific PRD capability/gate; plan task and interfaces; accepted decisions; exact owned files; predecessor contracts/commits; relevant wireframe guide and mapped frames for UI work; red/green tests, commands and expected results; forbidden scope and simulation/privacy boundaries. Tell it that other agents are working in the same repository, to preserve their edits, and to request ownership coordination before changing an unowned path. Use standard Claude Code subagents with isolated context and a task worktree for writing. Do not rely on built-in exploratory agents having read project instructions—supply the pointers explicitly. If subagent execution is unavailable, stop and ask; do not silently replace the requested method with one monolithic session or enable experimental agent teams by default.
3. Require the implementer to run the task's failing tests before the fix when prescribed, then green tests, typecheck, relevant regression suites, and task-specific emulator/browser checks. No skipped acceptance check can be recorded as passed. It should make atomic DSN-prefixed local commits and put exact commands, results, changed paths, commit IDs, limitations, and unresolved risks into the task record. A finished-looking UI or a worker's assertion is not verification. When its declared acceptance is complete, move the task to `review`; otherwise leave it in progress or record a real blocker.
4. Assign an **independent, fresh, read-only review subagent** after implementation. It must inspect the diff and behavior against the PRD, accepted decision, plan task, UI frames where applicable, and the changed tests. Ask it to check failure/race cases and this product's critical boundaries: owner/ally authorization, consent and retention, source provenance and prompt-injection resistance, non-settling simulated payment, explicit human choice, no fabricated bank/authority outcome, accessibility, and no secrets or real personal data. Require concrete findings with severity and file/line plus reproducible evidence; it must not merely approve the worker summary or make edits.
5. Return actionable findings to the owning implementer (or a fresh scoped fixer), rerun failing and affected regression checks, and obtain a fresh independent re-review of the corrected diff. Repeat until no material acceptance, security, privacy, or correctness finding remains. Record honest trade-offs and deferred risks in the canonical task/decision records. Do not close a task with an unresolved critical finding; if a real external decision or impasse remains, use `blocked` with exact evidence, owner, and next action while continuing unaffected tasks.
6. You, as integrator, verify scope/ownership and review evidence; merge the reviewed branch into **local** `main`; rerun relevant tests and link/format checks on integrated `main`; then and only then move the task to `done` with integration commit and post-integration evidence. Do not let a worker merge its own work. Reconcile dependent briefs with the actual integrated contracts before dispatching them. If a change to architecture, data contract, security/privacy, dependency, model, deployment, or user interaction is consequential, record it in `project/decisions/`; any product-scope change remains Proposed until the founder approves it.

Keep your own context lean: delegate file-level implementation and review, pass task-specific references rather than copying the entire PRD into every prompt, and reconstruct progress from Git and task records after any compaction/resume. Send the founder concise updates at meaningful milestones or when a decision is required; do not request approval for routine bounded engineering choices. Do not mark core work done because the demo merely looks plausible, and do not start stretch work before every Core MVP Cup-ready gate passes.

## Non-negotiable product and external-action boundaries

- This is one controlled, synthetic India-based Demo Bank/UPI case, not always-on call capture, a live bank integration, a real transfer, a real 1930 call, or an automated report. All prototype payment, Demo Bank, and authority acknowledgements must remain persistently labeled **Simulated**. The UI intervenes before OTP/authorization and never claims to have held or reversed an actual transfer.
- Browser code never talks directly to Firestore or Gemini; the authenticated API owns both. Gemini supplies validated, source-linked candidate facts, while deterministic policy and explicit human action own consequential state transitions. A pending submit intent never auto-settles on timeout or model outage. No scam probability, mental-state label, public blacklist, or caller-provided “official” contact route.
- Follow the approved wireframes for hierarchy, interaction, safety copy, and responsive guidance. They are not final branding or production markup. Verify keyboard operation, screen-reader names, contrast, touch targets, and 200% text scaling in the working UI.
- Never commit credentials, local paths, personal data, generated output, or workplace identity. Use a personal/no-reply Git identity. **Local commits are allowed; do not push new implementation commits, deploy, create cloud/billable resources, submit to the Cup, contact institutions, or perform real financial/reporting actions without separate founder authorization.** Implement local deployment wiring and tests where possible; clearly mark live-cloud gates blocked rather than pretending they passed. A cloud authorization blocker should not stop unrelated local work.
- Where exact SDK behavior or submission rules may have changed, verify current primary documentation before relying on it. Log the actual model ID and region; do not imply India-only model processing when the model endpoint is global.
